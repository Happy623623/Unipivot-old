# 탈퇴 때 내 폴더 훑기 구현 (`fix/F-06-delete-sweep`)

> 📝 기준: docs/탈퇴경쟁_구현.md 8장 · docs/첨부커밋_구현.md 8장 · API 명세 v0.4 4장(`DELETE /me`)·6장(`POST /files`)·13장
> 적용할 곳: **E(`탈퇴경쟁_구현.md`)를 합친 main** 위. E 위에서 만들고 시험했다(C·G와는 겹치는 파일이 없다 — 밤 PR을 모두 합친 트리에도 그대로 맞는다). web·DB는 안 바뀐다.
> 사용자가 고른 것(10/21 오전): 업로드 오류 코드는 `CONSENT_REQUIRED`, 폴더 목록을 못 받으면 502로 멈춤, PR은 api 둘을 묶어 하나.

두 가지를 한다.

1. **탈퇴 때 저장소의 내 폴더(`<user_id>/`)를 훑어 기록이 없는 파일도 지운다.** 지금 탈퇴는 `files`에 기록된 경로만 지운다. 그런데 올린 뒤 기록의 커밋이 정말 실패하면(E·G에서 "기록이 됐는지 모르면 파일은 둔다"로 정했다) 그 파일은 기록이 없어 탈퇴로도 못 지운다. 이제 폴더를 훑어 그런 파일까지 지운다.
2. **탈퇴하는 사이에 들어온 업로드의 답을 500 대신 `403 CONSENT_REQUIRED`로.** E 뒤로 그 업로드는 기록을 넣다가 외래 키에 걸려(프로필이 이미 지워짐) 올린 파일을 지우고 500 `INTERNAL_ERROR`를 냈다. 프로필이 없는 사용자에게 `PATCH /me/profile`이 하듯 "약관에 먼저 동의해 주세요"(`details.consent = terms_privacy`)로 답한다.

## 3. 합친 뒤 확인

**목록 호출은 실제 Supabase에 대고 아직 한 번도 돌려 보지 않았다**(샌드박스는 Supabase에 닿지 못한다. storage-js와 같은 본문을 보내고, 검토도 storage-api 코드 기준으로 맞다고 봤다). 그래서 합친 뒤 한 번은 꼭 실제로 본다.

1. 버리는 계정으로 로그인 → 포스터를 하나 올린다.
2. Supabase 대시보드 → Storage → `uploads` 버킷에서 그 계정 id 폴더에 **아무 파일이나 하나 더 올린다**(기록 없는 파일 흉내).
3. 설정 → 탈퇴 → 204, 로그인 화면 "탈퇴했어요".
4. 버킷에서 그 계정 id 폴더가 비었으면 된다(올린 포스터와 손으로 넣은 파일 둘 다 없어야 한다).
5. 탈퇴가 502로 멈추면 API 로그의 `탈퇴 중 내 폴더를 훑지 못했어요: …` 줄을 보내 줘(키 값은 로그에 안 남는다). 그때는 목록 답의 모양이 달라 멈춘 것이라 그 줄로 고친다.

## 6. 되돌림 시험

| 되돌린 것 | 잡은 시험 |

| I1 폴더를 안 훑음 | 기록 없는 파일 지우기 3개 |
| I2 목록 실패를 넘어감 | 목록 실패 → 502 |
| I3 저장소 설정이 틀려도 훑음 | 설정 없음·publishable 키 |

| I5 폴더 안으로 안 들어감 | 폴더 안으로·쪽 넘기기 |
| I6 다음 쪽을 안 받음 | 쪽 넘기기 |
| I7 내 폴더 밖·`..`도 받음 | `..` 경로 버리기 |
| I8 깊이 상한 없음 | 끝없이 깊은 폴더 |
| I9 목록 답이 배열인지 안 봄 | 빈 객체 |

## 7. 검토에서 고친 것

새 에이전트가 읽기만 하고 검토했다(storage-api·storage-js 기준으로 목록 본문·폴더 표시·이름 모양을 대조하고, 시험 153개를 다시 돌렸다).

| 지적 | 처리 |
| --- | --- |
| (중간) 명세가 낡았다: `DELETE /me`의 "파일이 없으면 저장소를 부르지 않는다"가 이제 틀리고(설정이 맞으면 늘 목록을 부른다 — 저장소가 멈추면 파일을 올린 적 없는 사람도 502), `POST /files` 오류 목록에 `403 CONSENT_REQUIRED`가 없다 | 명세 3곳을 고친다(9장) |
| (낮음) 저장소 밖에서 넣은 이상한 키(끝이 `/`라 이름이 빈 항목 등)가 있으면 그 사람의 탈퇴가 계속 502다 | 고른 대로(못 읽으면 멈춤) 둔다. 8장 |
| (낮음) offset으로 넘기는 사이 파일이 지워지면 하나를 건너뛸 수 있다 | 다음 탈퇴(다시 로그인해 다시 탈퇴)가 지운다. 8장 |
| (낮음) "다른 API가 하듯"은 과장이다 — `GET /me`와 피드는 프로필을 다시 만든다 | 주석을 "`PATCH /me/profile`도 같은 답"으로 고쳤다 |
| (잔소리) 시험이 Supabase가 보내지 않는 모양(`user-10/z.jpg`)을 쓴다 | 뺐다 |
| (잔소리) 시나리오 실행기의 가짜 저장소에 목록이 없다 | 넣었다 |

검토가 문제없다고 본 것:
- **목록 호출**: 주소(끝에 `/` 없음)·본문 필드가 storage-js `list`와 같다. `prefix`는 폴더 뜻이고 서버가 끝 `/`를 붙인다(`user-1`이 `user-10`에 걸리지 않는다). `name`은 마지막 한 칸, 폴더는 `id`·`metadata`가 null이다.
- **남길 것을 지우지 않는다**: 저장소에 쓰는 곳은 업로드·LMS 첨부 둘이고 둘 다 기록을 남긴다. 포스터 공고는 `poster_file_id → files(id) on delete set null`로만 가리키고, 원본 보기는 올린 사람만 연다. 훑기는 기록이 없는 것만 더 지운다.
- **두 단계 탈퇴와의 사이**: 훑기가 지운 파일의 기록이 그 뒤 커밋돼도 마지막 단계의 지우기는 "없음"으로 지나간다. 잠근 뒤 넣는 기록은 외래 키로 실패한다.
- 이름에 `_`가 든 폴더(`lecture_material`)는 서버의 LIKE 때문에 `lectureXmaterial`도 함께 걸리지만, 잘못 붙인 경로는 "없음"으로 지나가고 진짜 파일은 제 폴더에서 찾는다. id가 UUID라 남의 폴더에는 닿지 않는다.

## 8. 남은 것

- **목록 호출을 실제 Supabase로 확인**(3장). 모양이 다르면 탈퇴가 502로 멈춘다 — 로그 한 줄로 고칠 수 있다.
- 저장소가 멈추면 파일을 올린 적 없는 사람도 탈퇴가 502다(설정이 맞으면 늘 폴더를 훑으니까). 고른 대로다.
- 저장소 밖(S3 호환 주소·손)으로 넣은 이상한 키가 있으면 그 사람의 탈퇴가 502다. 그때는 그 키를 대시보드에서 지운다.
- 목록을 넘기는 사이에 지워진 파일 때문에 하나를 건너뛸 수 있다(다음 탈퇴가 지운다).
- 업로드 화면은 `CONSENT_REQUIRED`를 따로 다루지 않아 문구만 보인다(탈퇴한 탭은 곧 로그인 화면으로 간다).
