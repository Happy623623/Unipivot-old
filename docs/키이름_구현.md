# 저장소 키 이름 바꾸기 구현 (`chore/api-secret-key-name`)

> 📝 기준: docs/저장소새키_구현.md 7번("변수 이름은 그대로 둔다") · API 명세 v0.4 9장(공지 첨부)
> 적용할 곳: **main(4faad26)** 위. 다른 PR과 겹치는 파일이 없다. web·DB는 안 바뀐다.
> 사용자가 고른 것(10/21 오후): 새 이름 + 옛 이름도 받기.

저장소 키 환경 변수 이름을 `SUPABASE_SERVICE_ROLE_KEY`에서 **`SUPABASE_SECRET_KEY`**로 바꾼다. 값은 이미 Secret keys(`sb_secret_…`)라 이름이 값과 맞지 않았다.
**네 `api/.env`는 고치지 않아도 그대로 돈다** — 예전 이름도 읽고, 둘 다 있으면 새 이름을 쓴다.

| 값 | 결과 |
| --- | --- |
| 브랜치 | `chore/api-secret-key-name` |
| 파일 | 새 파일 1개(`api/tests/test_config.py`), 고친 파일 13개(앱 3개 — `config.py`·`lms/sync.py`·`uploads/storage.py`, 시험 6개, `.env.example`·`README.md`·`pyproject.toml`·`uv.lock`) + 명세 1곳(9장) |
| web·DB | 안 바뀜(마이그레이션 없음) |
| api(DB 있이) | 1641 passed |
| api(DB 없이) | 1275 passed, 366 skipped(샌드박스 — 네 PC는 1274 passed, 367 skipped일 것), ruff check·format 통과 |
| 되돌림 시험 | 5개 모두 시험이 잡음 — 6장 |

## 1. 정한 것

| 고른 것 | 이유 · 버린 선택지 |
| --- | --- |
| 설정 이름 `supabase_secret_key`, 읽는 이름은 `SUPABASE_SECRET_KEY` → `SUPABASE_SERVICE_ROLE_KEY` 순(`AliasChoices`) | 앞 이름이 이긴다. 같은 곳(환경 변수끼리, `.env` 안끼리)에 둘 다 있으면 새 이름 |
| 사용자에게 보이는 고칠 점 문구(저장소 설정 확인·탈퇴 502)는 새 이름으로 말한다 | 예전 이름으로 넣었어도 같은 값이라 새 이름으로 안내해도 된다 |
| `pydantic-settings` 최소 버전 2.4 → **2.14** | 검토에서 2.4·2.6·2.13은 이름이 둘인 설정의 출처 우선순위가 틀린다는 것을 찾았다(환경 변수의 예전 이름이 `.env`의 새 이름에 진다). 잠근 버전(2.15)은 맞다. `uv.lock`은 요구 범위 한 줄만 바뀐다 |
| 지난 구현 문서(`docs/*_구현.md`·`docs/README_기록.md`)는 고치지 않는다 | 그때의 기록이다. 기준 문서(명세)만 고친다 |

## 3. 합친 뒤 확인

1. **아무것도 안 바꿔도 된다.** `api/.env`의 `SUPABASE_SERVICE_ROLE_KEY`를 그대로 읽는다.
2. 이름을 바꾸고 싶으면 `api/.env`에서 `SUPABASE_SERVICE_ROLE_KEY=` 앞의 이름만 `SUPABASE_SECRET_KEY`로 고친다(값은 그대로, 채팅에 붙이지 않는다).
3. 어느 쪽이든 아래로 확인한다. 키 값은 찍지 않고 고칠 점만 찍는다(없으면 `ok`).

   ```powershell
   cd api
   uv run python -c "from app.config import get_settings; from app.uploads.storage import storage_settings_problem; print(storage_settings_problem(get_settings()) or 'ok')"
   ```

4. API를 다시 켜고 포스터를 하나 올려 보면 끝이다.

## 7. 검토에서 고친 것

새 에이전트가 읽기만 하고 검토했다(pydantic-settings 버전마다 직접 돌려 보고, 전체 시험을 다시 돌렸다).

| 지적 | 처리 |
| --- | --- |
| (중간) 명세 9장(공지 첨부)이 아직 `SUPABASE_SERVICE_ROLE_KEY`라고 쓴다 | 새 이름으로 고친다(9장) |
| (낮음) `pydantic-settings>=2.4`는 범위가 넓다 — 2.4·2.6·2.13은 출처 우선순위가 틀린다 | 최소 버전을 2.14로 올리고 출처 순서 시험을 더했다 |
| (낮음) 시험의 `tmp_path` 타입이 틀렸고, 셸에 저장소 주소·버킷이 있으면 예전 이름 시험이 흔들린다 | `Path`로 고치고 저장소 관련 환경 변수 다섯 개를 지우고 돈다 |
| (잔소리) `.env.example`의 예전 이름 안내가 저장소 주소 줄 바로 뒤라 그 이야기처럼 읽힌다 | `SUPABASE_SECRET_KEY=` 바로 위로 옮겼다 |
| (낮음) `model_copy(update={"supabase_service_role_key": …})`는 조용히 무시된다(검증을 안 거친다) | 코드·시험에는 이제 없다. 지난 구현 문서의 조각을 베낄 때만 걸린다 — 8장 |

검토가 문제없다고 본 것: 대소문자, `.env`의 두 이름과 줄 순서, `Settings(supabase_service_role_key=…)`(필드 이름이 `AliasChoices`에 있어 `populate_by_name`이 필요 없다), `model_dump()`의 키, `extra="ignore"`라 `.env`의 예전 이름이 오류를 내지 않는다는 것.

## 8. 남은 것

- 지난 구현 문서의 코드 조각은 예전 속성 이름(`supabase_service_role_key`)을 쓴다. 그대로 베끼면 `model_copy(update=…)`가 조용히 무시된다 — 지금 코드는 `supabase_secret_key`를 쓴다.
- 셸에 저장소 키와 `SUPABASE_URL`을 내보낸 채 시험을 돌리면 `test_lms_sync.py`의 시험 하나가 실패한다(전부터 그랬다 — 예전 이름일 때도 같다). `api/.env`는 시험에 안 읽혀서 상관없다.

````python
"""설정 이름(app/config.py). 저장소 키는 새 이름 SUPABASE_SECRET_KEY로 읽고, 예전 이름 SUPABASE_SERVICE_ROLE_KEY도 읽는다.

키 값은 시험용 모양만 쓴다(실제 키가 아니다).
"""

from pathlib import Path

import pytest

from app.config import Settings
from app.uploads.storage import storage_settings_problem

NEW = "sb_secret_" + "Nw5" * 10 + "a"  # 시험용 값이다
OLD = "sb_secret_" + "Od3" * 10 + "b"
PROJECT_URL = "https://abcdefghijklmnopqrst.supabase.co"


@pytest.fixture(autouse=True)
def no_storage_env(monkeypatch: pytest.MonkeyPatch) -> None:
    """셸에 저장소 설정이 있어도 이 시험은 그것과 상관없이 돈다."""
    for name in (
        "SUPABASE_SECRET_KEY",
        "SUPABASE_SERVICE_ROLE_KEY",
        "SUPABASE_URL",
        "SUPABASE_STORAGE_BASE",
        "SUPABASE_STORAGE_BUCKET",
    ):
        monkeypatch.delenv(name, raising=False)


def test_the_new_name_is_read(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setenv("SUPABASE_SECRET_KEY", NEW)
    assert Settings(_env_file=None).supabase_secret_key == NEW  # type: ignore[call-arg]


def test_the_old_name_still_works(monkeypatch: pytest.MonkeyPatch) -> None:
    """api/.env를 고치지 않아도 그대로 돈다."""
    monkeypatch.setenv("SUPABASE_SERVICE_ROLE_KEY", OLD)
    settings = Settings(_env_file=None, supabase_url=PROJECT_URL)  # type: ignore[call-arg]
    assert settings.supabase_secret_key == OLD
    assert storage_settings_problem(settings) is None


def test_the_new_name_wins_when_both_are_set(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setenv("SUPABASE_SECRET_KEY", NEW)
    monkeypatch.setenv("SUPABASE_SERVICE_ROLE_KEY", OLD)
    assert Settings(_env_file=None).supabase_secret_key == NEW  # type: ignore[call-arg]


def test_the_env_file_reads_either_name(tmp_path: Path) -> None:
    old = tmp_path / "old.env"
    old.write_text(f"SUPABASE_SERVICE_ROLE_KEY={OLD}\n")
    new = tmp_path / "new.env"
    new.write_text(f"SUPABASE_SECRET_KEY={NEW}\n")
    assert Settings(_env_file=old).supabase_secret_key == OLD  # type: ignore[call-arg]
    assert Settings(_env_file=new).supabase_secret_key == NEW  # type: ignore[call-arg]


def test_sources_keep_their_order_whichever_name_they_use(
    tmp_path: Path, monkeypatch: pytest.MonkeyPatch
) -> None:
    """환경 변수가 .env를 이기고, 코드에서 준 값이 환경 변수를 이긴다(이름이 달라도). pydantic-settings 2.14부터 맞다."""
    env_file = tmp_path / ".env"
    env_file.write_text(f"SUPABASE_SECRET_KEY={NEW}\n")
    monkeypatch.setenv("SUPABASE_SERVICE_ROLE_KEY", OLD)
    assert Settings(_env_file=env_file).supabase_secret_key == OLD  # type: ignore[call-arg]
    monkeypatch.delenv("SUPABASE_SERVICE_ROLE_KEY")
    monkeypatch.setenv("SUPABASE_SECRET_KEY", NEW)
    given = Settings(_env_file=None, supabase_service_role_key=OLD)  # type: ignore[call-arg]
    assert given.supabase_secret_key == OLD


def test_the_problem_text_names_the_new_variable() -> None:
    """고칠 점 문구는 새 이름으로 말한다(예전 이름으로 넣었어도 같은 값이다)."""
    found = storage_settings_problem(Settings(_env_file=None, supabase_url=PROJECT_URL))  # type: ignore[call-arg]
    assert found is not None and "SUPABASE_SECRET_KEY" in found and "SERVICE_ROLE" not in found
````
