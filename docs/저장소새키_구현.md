# 파일 저장소 — Supabase 새 키(`sb_secret_…`)로 올린다

> 📝 기준: PRD v0.9 F-13·F-54 · ERD v0.9 8장(비공개 버킷) · 2026-10-19
>
> 적용할 곳: **#65(공지 첨부 저장)까지 합친 main** 위 새 브랜치. **마이그레이션 없음** · 명세·PRD·ERD 안 바뀜

10/19 네 PC에서 공지 첨부 4개가 LMS에서는 다 받아졌는데 저장소에 올릴 때 모두 400으로 거절됐다. 원인은
둘이었다. 하나는 `.env`에 키가 아닌 값(프로젝트 ID, 그다음 publishable key)이 들어 있던 것이고, 이건 네가
고쳤다. 다른 하나는 **코드**다. 2025년 11월 뒤에 만든 Supabase 프로젝트에는 예전 `service_role` 키가 없고
secret key(`sb_secret_…`)만 있다. 그런데 우리 저장소 코드는 키를 `Authorization: Bearer`에만 실었고,
Supabase는 그 자리의 새 키를 JWT로 읽으려다 거절한다. 네 PC에서 secret key로 세 방식을 바로 비교했다.

| 같은 secret key를 실은 곳 | 실제 Supabase 답 |
| --- | --- |
| `Authorization: Bearer`만 (지금 코드) | 400 `AccessDenied: Invalid Compact JWS` |
| `apikey` + 같은 값의 `Authorization` | 200 |
| `apikey`만 | 200 |

그래서 새 키는 `apikey`에만 싣는다. 포스터 올리기, 계획서·포스터 받기, 탈퇴 때 파일 지우기도 같은 코드를
지나서 모두 같이 고쳐진다. 오늘 원인 찾기가 오래 걸린 이유인 "로그에 `400`만 남는 것"과 "키 모양이
틀려도 아무 말이 없는 것"도 같이 고쳤다.

| 값 | 결과 |
| --- | --- |
| 테스트 | **1490 passed**(1451 → +39) · DB 없이 1144 passed, 346 skipped |
| 동기화 E2E | 실제 Supabase 답을 그대로 흉내 낸 가짜 저장소에서 main은 `{"saved": 0, "failed": 1}`·로그 `(400).`(네 PC와 같음) → 이 PR은 `{"saved": 1, "failed": 0}`, 저장소에 파일·`files` 행이 생기고 저장소가 받은 머리값은 `apikey`뿐 |

## 정한 것

1. **새 키(`sb_`로 시작)는 `apikey`에만 싣고 `Authorization`은 비운다.** Supabase 안내가 "새 키는 `apikey`에
   싣고 `Authorization`은 비워 두라"이다. 같은 값을 둘 다에 실어도 지금은 200이지만, 그건 안내가 "예전
   방식과의 호환으로만 봐준다"고 한 경우라 기대지 않는다.
2. **예전 `service_role` 키(JWT `eyJ…`)는 `apikey`와 `Authorization` 둘 다에 싣는다.** 예전 프로젝트는 지금처럼
   된다. 이 키는 Supabase가 2026년 말에 없앤다고 했다.
3. **저장소가 거절하면 Supabase가 준 이유를 오류 문구에 붙인다.** 예:
   `파일 저장소가 요청을 거절했어요(400, AccessDenied: Invalid Compact JWS).` 이 문구는 **로그에만** 남는다.
   사용자에게는 지금처럼 정해 둔 문구(`502 STORAGE_API_ERROR`)가 간다. 이유 속에 키가 있으면 `[가림]`으로
   바꾸고, 한 줄로 펴서 120자에서 자른다. 본문이 JSON 객체가 아니면 상태 번호만 남긴다.
4. **서버를 켤 때 설정을 보고 고칠 점을 경고한다**(`파일 저장소 설정 확인: …`). 경우는 일곱이다.
   - 키나 주소가 비었다(원래 있던 경고, 문구 같음)
   - 버킷 이름이 비었다
   - 키에 빈칸·따옴표·보이지 않는 글자처럼 키에 없는 글자가 섞였다(복사하다 섞이는 것)
   - secret key가 너무 짧다 — 가려진 화면 글자만 옮겨 적었거나 잘렸다
   - publishable key(`sb_publishable_…`)다 — 권한이 없어 RLS에 막힌다
   - 키 모양이 아니다 — 오늘의 프로젝트 ID 같은 값
   - JWT인데 `role`이 `service_role`이 아니다 — 예전 프로젝트의 anon 키

   키 값은 보여 주지 않는다. 서버는 그대로 뜬다(경고만). 어떤 값이 와도 점검이 예외를 내지 않는다. JWT는
   서명을 보지 않고 `role`만 읽는다.
5. **머리값에 실을 수 없는 글자가 섞인 키는 아예 보내지 않는다**(`A-Z a-z 0-9 . _ -`만 받는다. 새 키와 JWT가
   쓰는 글자다). 보내다 깨지면 그 오류에 키가 통째로 실려 로그에 남기 때문이다. 이런 키는 없는 키로 보고,
   동기화는 첨부를 건너뛰고 업로드는 `502 STORAGE_API_ERROR`다. 앞뒤 빈칸은 떼고 쓴다.
6. **로그 가리기에 `sb_secret_…`를 더했다.** 새 키가 어쩌다 로그에 찍혀도 가린다. publishable key는 브라우저에
   두는 공개 값이라 가리지 않는다. 경고 문구 속 안내 `sb_secret_…`(말줄임표)는 가려지지 않는다.
7. **변수 이름 `SUPABASE_SERVICE_ROLE_KEY`는 그대로 둔다.** 바꾸면 네 `.env`·CI·문서가 같이 바뀌어야 한다. → 10/21 `SUPABASE_SECRET_KEY`로 바꿨다. 예전 이름도 읽는다(docs/키이름_구현.md).
   `.env.example`·`README.md`·설정 주석에 "Secret keys 값(`sb_secret_…`)을 넣는다"고 적었다.

````text
네 PC의 api/.env에는 이미 secret key가 들어 있다(10/19에 세 방식 비교를 돌린 그 값).

0. (합치기 전에 해도 된다) 실제 Supabase에서 받기·지우기도 apikey만으로 되는지 본다. 10/19에는 올리기만
   봤다. api 폴더에서 PowerShell에 통째로 붙여 넣는다. 키 값은 찍지 않고, 시험 파일은 지운다.

@'
import httpx
from app.config import get_settings

s = get_settings()
headers = {"apikey": s.supabase_service_role_key.strip()}
url = f"{s.storage_base_url}/object/{s.supabase_storage_bucket}/_check/ping.txt"
r = httpx.post(url, content=b"ping", headers={**headers, "Content-Type": "text/plain", "x-upsert": "true"})
print("upload ->", r.status_code, r.text[:120])
r = httpx.get(url, headers=headers)
print("download ->", r.status_code, r.content[:20])
r = httpx.delete(url, headers=headers)
print("delete ->", r.status_code, r.text[:120])
r = httpx.delete(url, headers=headers)
print("delete again ->", r.status_code, r.text[:120])
'@ | uv run python -

   upload·download·delete가 200이어야 한다. 마지막 줄(없는 파일 지우기)은 무엇이 오는지 보려는 것이다
   — 탈퇴를 다시 누를 때 이미 지운 파일을 "없으니 지나간다"로 볼 수 있어야 해서다.

1. API 서버를 PowerShell 창 하나에서만 다시 켠다. 시작 로그에 "파일 저장소 설정 확인" 줄이 없어야 한다.
   (있으면 그 줄이 무엇을 고칠지 말해 준다. 키 값은 찍히지 않는다)
2. 마지막 동기화에서 5분이 지난 뒤 학업 화면을 연다. 서버 창에
   POST https://….supabase.co/storage/v1/object/uploads/… "HTTP/1.1 200 OK" 줄이 첨부 수만큼 찍힌다.
3. Supabase SQL Editor에서 그 한 줄 쿼리를 다시 돌린다. last_save_step이 {"saved": 4, "failed": 0}.
   Storage → uploads → (네 id) → lecture_material에 파일 4개, 과목 공지 탭 첨부 옆이 "저장됨".
4. 거절되면 이제 서버 창에 이유가 같이 찍힌다. 예: (400, AccessDenied: new row violates row-level security policy)
   → publishable key가 들어간 것이다.
````

## 남은 것

- **문서함에서 저장한 파일 열기**(서명 URL 5분, `Content-Disposition: attachment`) — 첨부가 "저장됨"이 된 걸
  본 다음 PR로 하자던 그것이다.
- **변수 이름.** Supabase 쪽 이름이 secret key로 바뀌었으니 `SUPABASE_SECRET_KEY`로 바꿀지는 네가 정하면
  된다. 바꾸면 `.env`·CI·문서를 한 PR에서 같이 고친다.
- **실제 Supabase의 받기·지우기**는 "합친 뒤 확인" 0번으로 본다. 특히 없는 파일을 지울 때 오는 답이
  404가 아니라 400이면, 탈퇴를 다시 누를 때 이미 지운 파일에서 502로 멈춘다(예전부터 있던 길, 이 PR이
  바꾸지 않는다). 그렇게 나오면 따로 고친다.
- **예외를 `%r`로 찍는 로그**(동기화 경고 몇 곳)는 로그 가리기가 str만 봐서 repr 속 값을 못 가린다. 이 PR로
  키가 거기 닿는 길은 막았지만, 가리기가 repr도 보게 할지는 따로 정하면 된다.
- 예전 JWT 키는 이 프로젝트에 없어서 실제 Supabase에서는 못 봤다(가짜와 단위 시험으로만 봤다). 예전 키로 도는
  곳이 없으니 지금은 상관없다.
- 지난 구현 문서(`docs/포스터업로드_구현.md`·`docs/공지첨부저장_구현.md`)에는 service_role을 넣으라고 적혀

- Storage의 RLS 정책은 건드리지 않는다. 서버만 secret key(=service_role 권한)로 올리고 받는다.
