# 공지 첨부 커밋 오류 처리 구현 (`fix/F-54-lms-attachment-commit`)

> 📝 기준: docs/공지첨부저장_구현.md 8번 · docs/탈퇴경쟁_구현.md 8장 · 2026-10-21
> 적용할 곳: `main`(6948ebf, #82) 위. 그 트리에서 만들고 시험했다. 밤 PR C·E와 겹치는 파일은 없다(밤 PR 6개를 모두 합친 트리에도 패치가 그대로 맞는 것을 확인했다). web·DB는 안 바뀐다.
> **자리를 비운 동안 만든 PR이다.** 사용자에게 묻지 않고 권장안으로 골랐다. 탈퇴 경쟁 PR(E)의 검토가 남긴 것을 업로드와 같게 맞춘다.

LMS 동기화가 공지 첨부를 받으면 저장소에 올린 뒤 `files`에 기록한다. 기록하다 오류가 나면 올린 파일을 지운다(주인 없는 파일이 남지 않게). 그런데 **커밋 중 연결이 끊긴 오류**까지 같은 오류로 봤다. 커밋이 실제로 됐으면 기록은 남고 파일만 지워진다. 그러면 문서함에서 받을 때 "저장한 파일이 없어졌어요"가 되고, 그 첨부는 이미 받은 것으로 기록돼 있어 다음 동기화도 다시 받지 않는다. 업로드(`POST /files`)는 E에서 이 경우를 고쳤고, 이 PR은 LMS 첨부도 똑같이 맞춘다.

## 1. 정한 것 (사용자 부재 — 권장안)

| 고른 것 | 이유 · 버린 선택지 |
| --- | --- |
| 기록 넣기(`add_lms_attachment`)가 끝난 뒤의 오류에는 **파일을 지우지 않는다** | 그 뒤에 남은 일은 커밋뿐이다. 커밋이 됐는지 모르면, 지우는 것보다 두는 쪽이 덜 나쁘다. 안 됐으면 주인 없는 파일이 하나 남고 다음 동기화가 새 번호로 다시 받는다 |
| 같은 첨부가 먼저 들어와 **넣지 않았으면** 커밋 중 오류에도 지운다 | 우리 경로를 가리키는 기록이 없다. 두면 영영 주인 없는 파일이 된다(검토) |
| 그 첨부는 이번 동기화에서 "실패"로 센다 | 됐는지 모르니 저장했다고 하지 않는다. 기록이 됐으면 다음 동기화가 이미 받은 것으로 본다 |
| 기록 넣기에서 난 오류(그새 탈퇴해 외래 키에 걸림, DB가 멈춤)는 전처럼 지운다 | 그때는 커밋되지 않는다 |

## 3. 합친 뒤 확인

커밋 중 끊김은 손으로 만들 수 없다(시험이 본다). 따로 볼 것은 없다 — LMS 동기화가 평소처럼 첨부를 받으면 된다.

## 4. 구조

```text
AttachmentSaver._save
  받기 → 저장소에 올림 → transaction(): add_lms_attachment → recorded = (넣었나) → (블록을 나오며 커밋)
    오류, recorded 아님 → 올린 파일 지움 → "failed"(전과 같다)
    오류, recorded      → 파일은 둠, 로그 "기록이 저장됐는지 몰라 …" → "failed"
  added is None(그새 같은 첨부) → 지움 → "skipped"(전과 같다)
```

## 7. 검토에서 고친 것

새 에이전트가 읽기만 하고 검토했다. 블록을 나올 때 하는 일이 커밋뿐인지 psycopg·psycopg_pool 코드까지 읽어 확인했다(풀은 커밋 뒤 연결을 돌려줄 뿐 오류를 내지 않고, 마이그레이션에 미뤄 두는 제약이 없어 커밋 오류는 사실상 연결 오류뿐이다).

| 지적 | 처리 |
| --- | --- |
| (낮음) 같은 첨부가 먼저 들어와 넣지 않았는데도 "기록됨"으로 봐서, 커밋 중 끊기면 파일이 영영 주인 없이 남는다 | 넣었을 때만 "기록됨"(G3). 업로드(E)도 같은 자리가 있어 같이 고쳐 E 문서를 새 판으로 보냈다 |
| (낮음, 맞바꿈) 커밋이 정말 실패해 남긴 파일은 기록이 없어 탈퇴로도 못 지운다 | 8장 |

검토가 문제없다고 본 것: 다음 동기화는 커밋이 됐으면 이미 받은 것으로 건너뛰고, 안 됐으면 새 번호로 다시 받는다. "실패" 수는 실행 로그(`tool_calls.output`)에만 남는다. 탈퇴 잠금 뒤 들어온 기록 넣기는 외래 키 오류가 기록 넣기 안에서 나서 전처럼 지운다. 취소(`CancelledError`)는 전과 같이 잡지 않는다.

## 8. 남은 것

- 커밋이 정말 실패해 남은 파일은 기록이 없어 탈퇴로도 못 지운다(아주 드물다). 탈퇴 때 `<user_id>/` 앞머리로 저장소를 훑어 지우거나 주기적으로 주인 없는 파일을 지우면 막힌다 — 다음 일.
