# 탈퇴 — 저장소 키·주소가 틀려도 파일을 남긴 채 끝나지 않는다(F-06)

> 📝 기준: API 명세 v0.4 4장 `DELETE /me` · PRD v0.9 F-06 · 2026-10-19
>
> 적용할 곳: **main(445de94, #68)** 위 새 브랜치. 문서함 PR과 같은 파일(`storage.py`·명세)을 고쳐서 #68이 들어간
> main이어야 패치가 맞는다. **마이그레이션 없음** · 명세 2곳(PRD·ERD 안 바뀜)

탈퇴는 저장소가 "없는 파일"이라고 답하면 이미 지운 것으로 보고 지나간다(다시 누르기 때문, #67). 그런데 그 답이 늘
"없는 파일"인 것은 아니었다. **publishable key처럼 권한이 모자란 키로 지우면 저장소는 비공개 파일을 못 보고 같은
`400 NoSuchKey`로 답하고, 주소가 틀리면(경로가 붙은 `SUPABASE_URL` 등) 저장소가 아닌 곳이 `code` 없는 404로 답한다.**
둘 다 204로 "탈퇴했어요"가 되고, 기록은 지워지는데 파일은 저장소에 그대로 남는다. 기록이 없으니 설정을 고친 뒤에도 그
파일을 찾아 지울 길이 없다. 이 PR은 ① 파일이 있는 탈퇴에서 저장소 설정을 먼저 보고, 고칠 점이 있으면 **하나도
지우지 않고 `502 STORAGE_API_ERROR`로 멈춘다.** ② "이미 없음"은 **본문 `code`가 `NoSuchKey`일 때만** 받는다 — `code`
없는 404는 지우기 실패라 첫 파일에서 502로 멈춘다(②는 독립 검토가 찾았고, #67에서 정한 것을 바꿔서 네가 골랐다).

## 정한 것

1. **파일이 있는 탈퇴만 저장소 설정을 본다.** `storage_settings_problem()`(켤 때 보는 것, 문서함 받기 주소가 `NoSuchKey`를
   믿을지 정할 때 쓰는 것)이 고칠 점을 내면 저장소를 부르지 않고 멈춘다. 파일·Google 권한·프로필 어느 것도 바뀌지
   않는다. 파일이 없으면 저장소를 부르지 않으니 설정도 보지 않는다 — 저장소 설정이 없는 로컬에서도 탈퇴된다.
2. **응답은 지금과 같은 `502 STORAGE_API_ERROR`, 같은 문구다**("파일을 지우지 못해 탈퇴를 멈췄어요. 잠시 후 다시 시도해
   주세요."). 새 코드는 없다. 웹은 500대면 자기 문구("탈퇴하지 못했어요. 잠시 후 다시 눌러 주세요.")를 보여 줘서 화면도
   같다. 학생이 고칠 수 있는 일이 아니고, 서버를 고치면 다시 눌러서 끝난다.
3. **무엇을 고칠지는 서버 로그에만 남긴다**(경고). `파일을 지우기 전에 탈퇴를 멈췄어요. 저장소 설정 확인: <켤 때와 같은
   안내>`. 안내 문구에는 키 값이 없다(모양만 말한다).
4. **판정은 키·주소 모양만 본다**(문서함과 같은 기준). publishable key, anon JWT, 잘린 secret key, 빈 설정을 잡는다.
   저장소를 한 번 더 부르는 확인은 하지 않았다.
5. **"이미 없음"은 본문 `code`가 `NoSuchKey`일 때만이다**(HTTP 400이든 404·410이든). **#67의 "404·410은 그냥 이미 없음"을
   바꿨다.** `code` 없는 404·410(API 게이트웨이·PostgREST·웹 서버가 답한 것)은 지우기 실패라 탈퇴가 첫 파일에서 502로
   멈춘다. 지금 Supabase의 "없는 파일"은 400 `NoSuchKey`라 다시 누르기는 그대로 된다. 나중에 Supabase가 `code` 없이
   404만 주게 바뀌면 다시 누르기가 502로 막히는데, 파일이 남는 쪽이 아니라 멈추는 쪽이다(로그에 이유가 남는다).
6. 다른 지우기(업로드·공지 첨부 되돌리기)는 실패해도 기록만 남기는 곳이라 5가 바뀌어도 하는 일은 같다(로그 한 줄).
7. `routers/me.py`에는 알림 설정 응답 모델 `Settings`가 이미 있어서, 앱 설정은 `AppSettings`라는 이름으로 들여온다.

## 남은 것

- **판정은 키·주소 모양만 본다.** 모양은 맞는데 그 프로젝트의 키가 아닌 경우(다른 프로젝트의 secret key, 폐기한 키)는
  키 가드가 못 잡는다. 그런 키는 저장소 앞단에서 거절될 것이라(`NoSuchKey`가 아니라) 지우기 실패로 502가 되지만, 실제
  Supabase의 답은 못 봤다.
- **`SUPABASE_URL`이 다른 프로젝트를 가리키고 키도 그 프로젝트 것이면** 지우기는 그쪽 저장소에서 진짜 `NoSuchKey`로
  지나간다. 주소와 키를 한꺼번에 다른 프로젝트 것으로 바꾼 때라 드물다. 막으려면 지우기 전에 그 학생의 파일이 저장소에
  실제로 있는지 봐야 하는데, 앞서 파일만 지우고 멈춘 탈퇴(다시 누르는 경우)와 구별하기 어렵다. 버킷만 물어보는 확인으로도
  못 막는다(그 프로젝트에도 `uploads` 버킷이 있으면 지나간다).
- 주소 모양 검사(경로가 붙은 `SUPABASE_URL` 등)를 켤 때 경고에 넣는 일은 따로다. 지금은 업로드·받기·탈퇴가 그 404로
  실패하고 로그에 `no Route matched` 같은 이유가 남는다.
- `storage_paths`를 읽은 뒤 동기화·업로드가 새 파일을 넣으면 그 파일은 행만 cascade로 지워지고 저장소에 남는다(이 PR
  전부터 있던 경쟁 상태. 탈퇴 중에 동기화가 도는 드문 때다). → 10/21 지우기 직전에 잠그고 목록을 다시 받아 지운다(docs/탈퇴경쟁_구현.md).
- 켤 때 경고와 탈퇴 로그의 publishable key 안내는 "파일을 못 올려요"라고만 한다(고칠 곳은 같다).
- **로컬 E2E에서 가짜 저장소를 쓸 때도** 키는 `sb_secret_` 뒤 20자 이상(또는 service_role JWT) 모양이어야 파일이 있는
  학생이 탈퇴된다. 아니면 이제 502다(올리기는 키 글자만 봐서 전처럼 된다).
- 문서함(#68) 합친 뒤 확인 1은 정상이었다(10/19). 실제 Supabase의 받기 머리값은
  `attachment; filename="__ __ (__).txt"; filename*=UTF-8''<원래 이름>` 꼴이다 — 가짜 저장소(storage-api 코드 모양)와
  달리 `filename`은 한글을 `_`로 바꾼 대체 이름이다. 브라우저는 `filename*`를 쓴다(이 머리값 그대로 Chromium에서 받으면
  "확인 파일 (한글).txt"). 다음에 가짜 저장소를 만들면 이 모양으로 흉내 낸다. cors는 `*`라 받기를 fetch+blob으로 바꿀 수 있다.
- 앞 PR의 남은 것(받기를 fetch+blob으로, "더 보기" 공용 버튼 초점, 녹화 저장소 `signed_url`, `%r` 로그 가리기, 변수
  이름 `SUPABASE_SECRET_KEY`, 포스터 원본 보기, 강의자료 요약)은 그대로다.
