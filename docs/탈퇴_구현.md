# 탈퇴 — `DELETE /me`가 생겼다

> 📝 기준: API 명세 v0.4 4장 · ERD v0.9 7장 · PRD v0.9 F-06 · 2026-10-19
>
> 적용할 곳: **캘린더 연결 해제(2/3)까지 합친 main** 위 새 브랜치. README PR(3/3)과는 겹치지 않아 앞뒤 상관없다. **마이그레이션 없음**

명세 4장에 `DELETE /me`(P0, 탈퇴)가 적혀 있었는데 코드가 없었고, 설정 화면은 "탈퇴는 아직 준비
중이에요"를 띄우고 있었다. PRD 169줄이 F-06을 P0로 둔 이유가 "연동 해제·탈퇴·동의 철회는 개인정보
처리상 빠질 수 없다"라 만들었다. ERD 7장이 탈퇴를 "profiles 삭제 → cascade"로 정해 둬서 DB 쪽은 한
줄이고, 나머지는 **그 전에 바깥 것(파일·Google 권한)을 치우는 순서** 문제다.

| 값 | 결과 |

| 테스트 | **1399 passed**(1394 → +5) · DB 없이 1058 passed, 341 skipped |
| 브라우저(실제 모드) | 토큰·파일·프로필이 있는 사용자가 설정에서 탈퇴 → `DELETE /me` → **저장소 파일 삭제 → Google(가짜)에 폐기 → DB 0행** → 로그아웃 → 로그인 화면 "탈퇴했어요" → 설정에 다시 가면 로그인으로 |

## 정한 것

1. **순서는 파일 → Google 권한 → DB다.** 파일을 못 지우면 `502 STORAGE_API_ERROR`로 **멈추고 아무것도
   바꾸지 않는다.** 개인 파일을 저장소에 남긴 채 "탈퇴했어요"라고 할 수는 없다. 다시 누르면 처음부터
   다시 하고, 이미 지운 파일은 없는 것으로 지나간다(저장소의 `remove`가 404를 그냥 넘긴다).
2. **파일이 없으면 저장소를 부르지 않는다.** 그래서 `SUPABASE_SERVICE_ROLE_KEY`가 없는 로컬(지금 네
   `.env`)에서도 파일을 안 올린 사용자는 탈퇴가 된다.
3. **Google 권한은 연결 해제와 같은 함수로 거둔다**(`CalendarService.disconnect`). 거두지 못해도
   계속한다 — 연결 해제 PR에서 정한 대로다.
4. **Supabase 로그인 계정은 남긴다.** ERD 7장이 탈퇴를 "profiles 삭제"로 정했다. 프론트는 204를 받으면
   이 기기의 세션을 지우고 로그인 화면으로 보내고, 다시 로그인하면 동의부터 새로 시작한다. 계정까지
   지우려면 Supabase Auth 관리자 API를 서비스 키로 불러야 하는데, 그건 **네가 정할 일**이라 "남은 것"에
   뒀다.
5. **실행 로그는 남는다(사용자만 null).** ERD의 `agent_runs.user_id on delete set null`이다. 성공률·비용
   지표가 거기서 나와서 지우지 않는다. 공유 포스터 공고도 업로더만 비운다.
6. **파일 경로는 `files` 표에서 찾는다**(`storage_path`). 포스터·계획서·강의자료가 다 거기 적힌다.
   저장소 목록 API로 긁지 않은 것은, 올렸는데 기록을 못 남긴 파일은 올릴 때 이미 되돌리기 때문이다.
7. **화면은 "탈퇴" 글자를 입력해야 단추가 열린다**(원래 있던 확인 방식). 문구에 무엇이 남는지 적었다
   — 공유 포스터는 이름 없이, 캘린더에 넣은 일정은 그대로.
8. **로그인 화면에 `?notice=deleted` 안내를 더했다.** 오류 빨강이 아니라 초록으로 "탈퇴했어요".

## 남은 것

- **Supabase 로그인 계정까지 지울지.** 지금은 남긴다(ERD 7장). 지우려면 서비스 키로 Auth 관리자
  API(`DELETE /auth/v1/admin/users/{id}`)를 부르는 한 단계가 더 붙고, 그러면 세션이 바로 무효가 된다.
  "모든 개인 데이터"에 로그인 계정(이메일·이름)까지 넣을지는 네가 정하면 된다 — 정하면 `account.py`에
  한 단계 더하는 일이다.
- **파일을 지운 뒤 DB에서 실패하면** 파일만 없는 계정이 남는다(프로필은 그대로). 다시 탈퇴하면 된다.
- 시험용 계정으로 실제 Supabase·Google에 대고 한 번 돌려 봐야 한다("합친 뒤 확인").

## 코드

새로 만드는 파일 3개다.

#### `api/app/account.py`

```python
"""탈퇴 (API 명세 4장 `DELETE /me`, F-06). 한 번에 셋을 한다 — 파일, Google 권한, DB.

순서가 중요하다.
1. **저장소의 파일**을 먼저 지운다. 실패하면 502로 끝내고 아무것도 바꾸지 않는다 — 개인 파일을
   남긴 채 "탈퇴했어요"라고 할 수는 없다. 다시 누르면 처음부터 다시 한다
2. **Google 캘린더 권한**을 거둔다(되는 만큼. 연결 해제와 같은 함수)
3. **profiles 행**을 지운다. 딸린 행(토큰·설정·알림·플래너·판정·파일 기록·구독)은 cascade로
   사라지고, 공유 포스터 공고의 업로더와 실행 로그의 사용자는 null이 된다(ERD 7장)

Supabase 로그인 계정은 남는다 — ERD 7장이 탈퇴를 "profiles 삭제"로 정했다. 다시 로그인하면 동의부터
새로 시작한다. Google 캘린더에 이미 넣은 일정은 지우지 않는다(명세 4장).
"""

import logging

from app.calendar.service import CalendarService
from app.errors import ApiError
from app.repositories.files import FileRepository
from app.repositories.profiles import ProfileRepository
from app.uploads.storage import StorageError, SupabaseStorage

logger = logging.getLogger(__name__)

STORAGE_FAILED = "파일을 지우지 못해 탈퇴를 멈췄어요. 잠시 후 다시 시도해 주세요."


async def delete_account(
    user_id: str,
    *,
    files: FileRepository,
    storage: SupabaseStorage,
    calendar: CalendarService,
    profiles: ProfileRepository,
) -> bool:
    """탈퇴. 지울 프로필이 있었으면 True다(없어도 204 — 두 번 눌러도 같다)."""
    paths = await files.storage_paths(user_id)
    for path in paths:
        try:
            await storage.remove(path)
        except StorageError as exc:
            logger.warning("탈퇴 중 파일을 지우지 못했어요: %s", exc)
            raise ApiError(502, "STORAGE_API_ERROR", STORAGE_FAILED) from exc
    await calendar.disconnect(user_id)
    return await profiles.delete(user_id)
```
