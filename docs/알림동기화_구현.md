알림함 화면(`/notifications`)과 헤더 알림 패널은 같은 알림 목록을 **따로 한 벌씩** 들고 있다(`useNotifications`를 하나씩 쓴다). 그래서 한쪽에서 읽은 알림이 다른 쪽에는 안 읽음으로 남았다.

- 알림함 화면에서 종을 열고 "모두 읽음"을 누른 뒤 닫으면, 뒤에 있던 알림함 줄은 그대로 연한 파란 바탕(안 읽음)이었다. 부제와 배지만 0이 됐다.
- 알림함에서 줄을 읽고 패널을 열면, 패널이 다시 받는 동안 전에 받아 둔 목록이 안 읽음으로 보였다.
- 받던 중인 응답이 늦게 오면(더 보기 등) 그 안의 옛 상태가 방금 읽은 것을 덮었다.

이번 PR은 **저장된 읽음 처리를 같은 탭의 다른 목록에도 바로 입힌다.**

## 1. 정한 것 (사용자 부재 — 모두 권장안)

| 고른 것 | 이유 · 버린 선택지 |
| --- | --- |
| **같은 탭** 안의 두 목록만 맞춘다 | 문제가 된 것은 알림함 화면 위에 패널을 연 경우다. 다른 탭은 패널을 열 때·화면을 다시 열 때 서버에서 새로 받는다. 탭끼리까지 맞추려면 BroadcastChannel이 더 필요해서 뺐다(8장) |
| 훅 안의 작은 알림(모듈 안 리스너 집합)으로 넘긴다 | 레포 규칙이 상태관리 라이브러리를 막는다. 두 목록을 한 스토어로 합치면 필터(전체·안 읽은 알림)·쪽 상태가 달라 고칠 곳이 커진다. 화면 쪽 코드는 그대로다 |
| **서버에 저장된 것만** 알린다 | 누르자마자 보이는 표시(낙관)는 누른 목록에서만 한다. 실패하면 그 목록만 되돌린다. 낙관 단계부터 알리면 되돌림도 알려야 해서 복잡해진다 |
| 받던 중인 응답에는 **다시 입힌다** | 요청을 보낸 뒤 들은 읽음 처리(최근 50건)를 늦게 온 쪽에 입히고, 안 읽은 수도 그때 들은 것을 쓴다. 버린 선택지: 늦은 응답을 버리고 다시 받기 — `generation`이 바뀌어 "더 보기" 안내가 "목록이 바뀌어 처음부터 다시 불러왔어요"로 잘못 나간다 |
| 저장 실패로 되돌릴 때도 그새 저장된 것은 남긴다 | 알림함에서 누른 읽음이 저장 중일 때 패널 "모두 읽음"이 저장되고 앞의 것이 실패하면, 누르기 전 상태로 되돌리면 안 읽음·배지 수가 서버보다 많아진다(검토) |
| "모두 읽음"은 **누른 시각까지 보낼 때가 된 알림**에만 입힌다 | 서버는 그때 보낼 때가 된 알림만 읽음으로 한다. 그 뒤에 보낼 때가 된 알림이 늦게 처리된 첫 쪽에 섞여 오면 안 읽음으로 둔다(검토) |
| 늦은 쪽의 안 읽은 수는 들은 것으로, 단 그 쪽이 "모두 읽음" 뒤에 센 것이면 쪽의 수로 | 쪽에 "모두 읽음" 시각 뒤에 보낼 때가 된 안 읽은 알림이 있으면 서버가 그 뒤에 센 것이다. 그때 들은 0으로 덮으면 안 읽은 줄이 보이는데 배지가 0이 되고 "모두 읽음"도 막힌다(검토) |
| 목록을 받기 전인 쪽(한 번도 안 연 패널)은 수를 받지 않는다 | 그래야 패널이 자기 목록을 받을 때까지 "모두 읽음"이 막혀 있다(기존 규칙, 검토) |
| "안 읽은 알림" 탭에서 읽음이 된 줄은 그 자리에 남는다 | 전과 같다(누른 자리가 그대로 보여야 한다) |

## 3. 합친 뒤 확인

실제 모드로 켜고(안 읽은 알림이 몇 개 있는 계정) 브라우저에서 본다.

1. `/notifications`를 연다 → 종을 누른다 → 패널의 **모두 읽음** → Esc. 뒤의 알림함 줄이 모두 흰 바탕이고 부제가 "읽지 않은 알림이 없어요"면 된다(전에는 줄이 파란 채로 남았다).
2. 같은 화면에서 **안 읽은 알림** 탭으로 바꾸고 1을 다시 한다. 줄은 그 자리에 남고 흰 바탕으로 바뀌면 된다.
3. 개발자 도구 Network를 **Offline**으로 두고 패널의 모두 읽음 → "읽음 처리를 저장하지 못했어요"가 나오고, 닫았을 때 알림함 줄은 그대로 파란 바탕이면 된다. Online으로 되돌린다.

## 4. 구조

```text
useNotifications (목록 하나마다 하나)
  read·readAll 저장 성공 → announce({ids | "all", readAt, unread})
        └→ 같은 탭의 모든 useNotifications(자기 포함)
             · 받아 둔 줄에 읽음을 입힌다(all은 scheduled_at ≤ readAt인 것만)
             · 안 읽은 수 = 서버가 센 수(아직 목록을 안 받았으면 null 그대로)
             · heard에 순번과 함께 적는다(최근 50건)
  첫 쪽·더 보기 응답 → 보낸 뒤 들은 것(heard)을 다시 입히고, 안 읽은 수도 그것으로
  저장 실패 → 그 줄만 되돌리고, 누른 뒤 들은 것을 다시 입힌다(undo)
배지: NotificationPanel·Notifications 화면의 effect가 unread를 AppShell로 올린다(전과 같다)
```

## 7. 검토에서 고친 것

새 에이전트가 읽기만 하고 두 번 검토했다(두 번째는 고친 것을 다시 봤다).

| 지적 | 처리 |
| --- | --- |
| (중간) 읽음 저장이 실패해 되돌릴 때 누르기 전 상태로 돌아가, 그사이 다른 목록에서 저장된 "모두 읽음"까지 지운다. 배지가 서버보다 많아진다 | 누를 때 순번을 적어 두고, 되돌린 뒤 그 뒤에 들은 것을 다시 입힌다. 수도 그 뒤에 들은 것으로(D8·D9) |

| (낮음) 한 번도 안 연 패널이 다른 쪽의 수를 받아 목록을 받기 전에 "모두 읽음"이 눌린다 | 목록을 받기 전에는 수를 받지 않는다(D11) |
| (낮음) 응답이 거꾸로 오면 옛 수가 이긴다(전부터 있었다) | 다음 저장·받기에서 맞는다. 8장 |
| (잔소리) 불필요한 형 변환 | 뺐다 |

검토가 문제없다고 본 것:
- **StrictMode**: 리스너는 집합이라 두 번 붙지 않는다. 다시 입히기는 몇 번 해도 같다.
- **필터 바꾸기**: 그사이 들은 것은 새 목록에 입혀진다.
- **"더 보기" 초점**: 줄 id·순서는 그대로라 `useLoadMoreFocus`는 그대로 동작한다.
- **정리**: 화면을 닫으면 리스너를 뗀다. 목록마다 최근 50건만 든다.
- **레포 규칙**: 상태관리 라이브러리를 더하지 않았다. 파일은 251줄이다.

## 8. 남은 것

- **다른 탭**은 맞추지 않는다. 패널을 열거나 화면을 다시 열면 서버에서 새로 받는다.
- **PC 시계가 서버보다 늦으면**, "모두 읽음" 직전 몇 분 안에 보낼 때가 된 알림이 서버에서는 읽음인데 다른 쪽 목록에는 안 읽음으로 남을 수 있다. 수와 배지는 맞고, 다음에 받으면 맞는다. 시계가 빠르면 거꾸로 그 몇 분 안의 새 알림이 읽음으로 보일 수 있다(원래 문제가 그 틈으로 줄었다).
- **응답이 보낸 순서와 다르게 오면** 잠깐 옛 수가 보일 수 있다. 다음 저장·받기에서 맞는다(이 PR 전부터 있던 것).
- 줄을 눌러 다른 화면으로 간 뒤 읽음 저장이 실패하면 그 자리에서 알리지 못한다(전과 같다).
