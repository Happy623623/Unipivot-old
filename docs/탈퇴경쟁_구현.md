> 📝 기준: docs/탈퇴_구현.md · docs/탈퇴저장소가드_구현.md "남은 것" · 인수인계 7장 6

> **자리를 비운 동안 만든 PR이다.** 사용자에게 묻지 않고 범위와 방식은 모두 권장안으로 골랐다. 고른 것은 1장에 적었다.
> **새 판(10/21 새벽)**: 먼저 보낸 판에서 업로드 정리 한 줄(충돌로 넣지 않은 때)과 시험 하나를 더했다. 먼저 받은 판은 버리고 이것을 써 줘.

탈퇴(`DELETE /me`)는 내 파일 목록을 받아 저장소에서 지우고, Google 권한을 거두고, 프로필을 지운다(딸린 행은 cascade). 그런데 **목록을 받은 뒤에** 업로드나 LMS 첨부 저장이 새 파일을 남기면, 그 파일 기록은 cascade로만 지워지고 **파일은 저장소에 남았다.** 기록이 없으니 다시 탈퇴해도 못 찾는다. 탈퇴 중에 동기화가 도는 드문 때지만, "탈퇴하면 사용자 데이터를 지운다"는 레포 규칙에 어긋난다.

그 김에 저장소 주소 검사의 작은 구멍 하나(빈 `?`·`#`)도 막는다(api 꼬리 PR 8장에 남긴 것).

## 1. 정한 것 (사용자 부재 — 모두 권장안)

| 고른 것 | 이유 · 버린 선택지 |
| --- | --- |
| **두 번 받는다**: 파일 지우기 → Google → **프로필을 잠그고(for update) 목록을 다시 받아** 새로 생긴 것만 지움 → 프로필 지우기 | 잠근 뒤로 이 사용자의 파일 기록을 넣는 요청은 외래 키 확인에서 탈퇴가 끝날 때까지 기다렸다가 프로필이 없어 실패하고, 그쪽이 방금 올린 파일을 지운다. 잠그기 전에 들어온 것은 두 번째 목록에 보인다 |
| 잠금은 **마지막 단계에서만** | 처음엔 맨 앞에서 잠갔다. 그러면 저장소·Google을 부르는 몇 초~수십 초 동안 그 사용자의 다른 요청(LMS 동기화·준비하기·판정)이 기다리고, 딸린 행을 먼저 잠근 쪽과 **교착**이 생겨 탈퇴가 500이 됐다(검토가 실제 Postgres로 재현). 지금은 보통 잠금이 `DELETE` 한 번 길이(전과 같다) |
| 지운 것은 다시 지우지 않는다 | 경로에 새 uuid가 들어 있어 같은 경로가 다시 생기지 않는다 |
| 업로드: **기록 넣기가 실패하면** 방금 올린 파일을 지우고 오류는 그대로 | 탈퇴가 끝나 외래 키에 걸린 업로드가 고아 파일을 남기지 않게. LMS 첨부 저장은 이미 그렇게 한다 |
| 업로드: 커밋 중 오류에는 **지우지 않는다** | 커밋이 됐는지 모르는데 지우면 기록이 없는 파일을 가리키고, 같은 파일을 다시 올려도 "이미 올린 파일"이 돼 스스로 못 고친다(검토). 지우기는 DB 연결을 돌려준 뒤에 한다. 같은 파일이 먼저 들어와 **넣지 않았으면**(충돌) 지켜야 할 기록이 없으니 커밋 중 오류에도 지운다(세 번째 검토) |
| 실패한 업로드는 500 그대로 | 탈퇴한 계정의 요청이라 따로 문구를 만들지 않았다(8장) |
| 저장소 주소: `SUPABASE_URL`의 빈 `?`·`#`, `SUPABASE_STORAGE_BASE`의 `?`·`#`도 막는다 | 뒤에 `/storage/v1/…`을 붙이면 쿼리가 되어 엉뚱한 곳이 답한다. 로그인 쪽(api 꼬리 PR)과 같은 기준 |
| 문서 | 탈퇴 저장소 가드 기록의 "남은 것" 한 줄(9장). 명세는 바뀌지 않는다(응답·순서의 겉모습이 같다) |

## 3. 합친 뒤 확인

경쟁은 손으로 만들기 어렵다(시험이 실제 Postgres로 본다). 손으로는 평소 탈퇴가 그대로인지만 본다.

1. 버리는 계정으로 포스터를 하나 올리고 설정 → 탈퇴 → 204, 로그인 화면 "탈퇴했어요".
2. Supabase 대시보드 Storage의 `uploads` 버킷에서 그 계정 id 폴더가 비었는지 본다.
3. API를 켤 때 로그에 `파일 저장소 설정 확인: …` 줄이 없으면 주소 검사도 문제없다.

## 5. 확인한 것

| 확인 | 결과 |
| --- | --- |
| 탈퇴 전체(실제 SQL) | 첫 파일을 지우는 사이 다른 연결이 새 파일 기록을 남기고 커밋 → 두 번째 목록으로 그것도 지움, `files` 0행, 프로필 없음 |
| 잠금(실제 SQL, 연결 둘) | 잠근 뒤 파일 기록 넣기는 기다린다(`lock_timeout` 300ms에 걸림) → 탈퇴가 커밋되면 외래 키 오류 |
| 순서(단위) | 첫 목록은 잠그지 않고, 두 번째 목록은 잠근 뒤. 새로 생긴 파일만 한 번 더 지운다 |
| 업로드(단위) | 기록 넣기가 외래 키에 걸리면 올린 파일을 지운다(연결을 돌려준 뒤). 커밋 중 연결이 끊기면 지우지 않는다. 같은 파일이 먼저 들어와 넣지 않았는데 커밋 중 끊기면 지운다 |
| 주소 검사(단위) | `…supabase.co?`·`…#`·`…/?` → "경로가 붙어 있어요", 저장소 주소 `…/storage/v1?`·`#x` → "?나 #가 들어 있어요". 값은 안 보인다 |
| 전체 | DB 있이 1609 passed, DB 없이 1243 passed, 366 skipped, ruff check·format 통과 |

## 7. 검토에서 고친 것

새 에이전트가 읽기만 하고 두 번 검토했다(실제 Postgres를 따로 띄워 교착을 재현하고, 고친 뒤 시험 140개를 다시 돌렸다).

| 지적 | 처리 |
| --- | --- |
| (중간) 맨 앞에서 잠그면 저장소·Google을 부르는 동안 잠금을 쥔다. LMS 동기화(과목 저장)·준비하기(계획 잠금)가 딸린 행을 먼저 잠근 뒤 새 행을 넣으면 교착이 되고, 탈퇴가 500으로 끝난다(파일·Google은 이미 지운 뒤). 재현함 | 잠금을 마지막 단계로 옮기고 목록을 다시 받는다(E6). 보통 잠금 길이가 `DELETE` 한 번과 같아 전과 같다(두 번째 검토 확인) |
| (낮음~중간) 그동안 그 사용자의 다른 요청이 오래 기다리고, 판정 잠금의 `assert`가 500을 낸다 | 위와 같이 짧아졌다. `assert`는 전부터 있던 아주 짧은 틈이다 |
| (낮음) 업로드 정리가 커밋 오류까지 잡아, 커밋된 기록의 파일을 지울 수 있다 | `add`가 끝나기 전 오류만 지운다(E8) |
| (낮음, 두 번째) 정리가 DB 연결을 쥔 채 저장소를 부른다 | 블록을 나온 뒤 지운다(시험이 연결을 돌려준 뒤인지 본다) |
| (잔소리) 외래 키 오류가 `ApiError`가 아니라 500이다 | 8장 |
| (낮음, 세 번째 — LMS 첨부 PR 검토에서) 충돌로 넣지 않았는데 커밋 중 끊기면 파일을 두어 영영 주인 없는 파일이 된다 | 넣었을 때만 "기록됨"(E12) |

검토가 문제없다고 본 것:
- **같은 요청 안의 교착**: 탈퇴 요청은 연결 하나(의존성 캐시)만 쓰고, 실행 로그(별도 풀)를 쓰지 않는다.
- **두 번 받기**: 잠근 뒤의 목록은 그 전에 커밋된 기록과, 넣는 중이던 기록(잠금을 기다린 뒤)을 모두 본다.
- **다시 누르기**: 처음 지우기가 중간에 실패해도 다시 누르면 처음부터 다시 받고, 이미 지운 파일은 "없음"으로 지나간다.
- **LMS 첨부**: 실패하면 올린 것을 지우는 코드가 이미 맞다.

## 8. 남은 것

- **두 번째 단계에서 실패하면**(잠근 뒤 새로 생긴 파일을 못 지움 등) Google 권한은 이미 거둔 뒤다. 캘린더가 "연결됨"으로 남지만 다음에 쓰면 다시 연결하라고 하고, 다시 탈퇴하면 끝난다(검토: 거둔 토큰을 다시 거두는 것도 성공으로 받는다). Google을 잠금 안으로 옮기면 잠금이 다시 길어져서 이대로 둔다.
- 새로 생긴 파일을 지우는 동안에는 잠금을 쥔다(드문 때. 파일 수만큼).
- 탈퇴 중에 올린 업로드는 500 `INTERNAL_ERROR`다(탈퇴한 계정이라 화면은 곧 로그인으로 간다). 따로 문구가 필요하면 명세 13장 코드부터 정한다.
- LMS 첨부 저장(`app/lms/files.py`)도 커밋 중 오류에 파일을 지운다 → 밤 PR G(`첨부커밋_구현.md`)에서 맞춘다.
- 커밋이 정말 실패해 남긴 파일은 기록이 없어 탈퇴로도 못 지운다(아주 드물다). 탈퇴 때 `<user_id>/` 앞머리로 저장소를 훑어 지우면 막힌다 — 다음 일. → 10/21 훑는다, 탈퇴 중 업로드는 403 `CONSENT_REQUIRED`(docs/탈퇴폴더훑기_구현.md).
- 환경 변수 이름을 `SUPABASE_SECRET_KEY`로 바꿀지(사용자가 정한다)
